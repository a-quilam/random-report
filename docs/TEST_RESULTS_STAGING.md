# Закрытая staging: приёмка нового HEAD на реальных источниках (t_a831193f)

Отчёт об интеграционной проверке объединённого HEAD в закрытой staging на
доверенном локальном сервере, через операторский preflight/runner. Значения
секретов и содержимое закрытых источников сюда не переносятся: ниже только
статусы, счётчики, идентификаторы релизов и проверяемые утверждения.

## 1. Что именно проверялось

| Предмет | Как проверено | Результат |
|---|---|---|

| Новый HEAD в закрытой staging | `staging-read.py` на `/home/agent/projects/random-report` (привязка к старому checkout снята) | 3 цикла подряд, exit 0, оба источника ok/complete |
| Приватные правила (последняя ревизия) | `staging-rules.py` → `staging-policy.json` + `staging-events.json` | 8 счетов-площадок, 1 исключённый подкалендарь, контуры собраний/аренды, режим собраний `contains` |

## 2. Дефекты, найденные staging-проверкой, и их исправления

Проверка не была формальностью: она вскрыла семь настоящих дефектов, каждый
закрыт кодом, тестом и записью в контрактах.

1. **Ночной цикл игнорировал приватные правила календаря.** Загрузчик читал
   только версию стола, поэтому документированные `TEAMUP_*` и приватный файл
   молча не применялись. `projection.policy.event_mapping_for` реализует
   документированный приоритет (стол → приватный файл → окружение) для ночного
   CLI и веб-сборки. (`docs/CALENDAR.md` §4, `docs/DOMAIN.md` §11.13)
2. **Правило собраний было неполным.** Записанная владельцем форма
   `source_title_contains_word` (без учёта регистра) не поддерживалась: было
   только точное совпадение. Добавлен явный режим `meeting_match`
   (`exact` по умолчанию, `contains` — владельческий), неизвестное значение
   режима отвергается. (`docs/DOMAIN.md` §11.14)
3. **Повторный запуск ломался на источнике Teamup.** `modifiedSince` уходил
   вместе с диапазоном дат, а API отвечает на это 400 «Invalid request»
   (проверено живым read-only запросом: фильтр изменений вообще не принимает
   диапазон дат и отдаёт мастер серии вместо экземпляров; changelog покрывает
   30 дней). Первый цикл проходил, каждый следующий падал. Теперь окно читается
   целиком, а changelog запрашивается отдельным вызовом только для явных
   удалений и только внутри 30 дней. (`docs/INGEST.md` §7.18, `docs/DOMAIN.md`
   §11.15)
4. **Жизненные issue источника не закрывались ничем.** Их id содержат дату, а
   сопоставить их нечем: прежняя ошибка Teamup (реальная ошибка opaque version)
   осталась бы открытой навсегда. Источник, успешно прочитанный в цикле, теперь
   закрывает свои прежние `source_failed`/`source_partial` с аудитом; в staging
   `resolved` = 3, новых замечаний нет. (`docs/INGEST.md` §7.20)
5. **Отсутствие read-only истории Telegram писалось как ошибка каждую ночь.**
   Это документированное нормальное состояние раздела: теперь оно видно как
   `not_configured` в payload и в покрытии, а не как вечно открытая issue.
   (`docs/INGEST.md` §7.19)
6. **Раздел календаря не относился к периоду релиза.** Все 38 релизов разных
   периодов несли одинаковые числа «за всё время» (457 событий, 54 собрания) —
   против требования фильтрации по месяцу/году. Теперь запись входит в период
   своего московского дня начала; 38 релизов дают 16 разных наборов агрегатов.
   (`docs/DOMAIN.md` §§7, 11.16)
7. **`verify-backup` не мог проверить зашифрованную копию.** Файл `*.enc`
   открывался как SQLite и падал трейсбеком «file is not a database». Теперь
   зашифрованная копия расшифровывается в приватный временный каталог и
   проверяется, без пароля — отказ словами, а не ошибкой драйвера.

Отдельно: **факты в закрытой staging были записаны прежним нормализатором.**
Старый checkout превращал любую строку с двумя счетами в перевод (так работает
реальная схема Zenmoney), поэтому в хранилище лежало 7392 «крыла перевода» из
7394 строк, а публичные суммы выходили нулевыми. Факты пересобраны из источника
штатным путём (сброшенный курсор = полный resync): 3774 движения, из них 150
крыльев (75 переводов), остальное — обычные операции; суммы и категорийный отчёт
стали содержательными (см. §4).

## 3. Что дал реальный цикл

* Миграции схемы применились на живой БД staging: 3 → 5 (ревизия — непрозрачный
  токен, пассивный inbox).
* Teamup: 459 записей (все пять подкалендарей; исключённый не даёт ни списков,
  ни итогов). Ревизии — непрозрачные токены (смесь цифровых и hex), реальная
  ошибка opaque version не воспроизводится: новая запись `source_failed` не
  появилась, прежняя закрыта.
* Zenmoney: полный diff, 3774 движения, 8 снимков баланса.
* Telegram: снимок подписчиков ok/complete; история — `not_configured` (нет
  согласованной read-only сессии), inbox неполон по построению.
* Новости: `coverage=partial` с причинами, провайдер LLM не вызывался (0 строк
  бюджета), платных сервисов нет.

## 4. Публичные данные после пересборки (структурно)

* 38 релизов (все целые месяцы с данными, годы и текущий незавершённый месяц);
  содержимое различается по периодам.
* Раздел событий текущего периода: открытые 17, по записи 6, закрытые 2,
  закрытая аренда 2, собрания 3 (публикуются как московская дата + константа).
* Денежный раздел: контур подтверждён; категории — только
  «требуют классификации» (обезличенно), метки `unclassified_present`,
  `subsidy_unknown`, `coverage_not_applicable`, `period_incomplete`,
  `completeness=partial`. Исходные названия категорий не публикуются, счета
  A1–A8 — контур площадки, ликвидность решает тип счёта (подтверждённый остаток
  публикуется как суммарный).
* В публичном JSON/HTML/CSV нет ни одного исходного идентификатора счёта или
  подкалендаря (проверено по значениям операторских правил).
* `web check`: 312 страниц, 0 проблем; `web export`: 320 файлов; локальный HTTP:
  12 маршрутов 200 (сырой сокет), приватная БД не открывалась.

## 5. Воспроизведение

```
cd <закрытый каталог доступа (вне репозитория)>
python3 verify-sources.py                    # preflight: доступы (только чтение)
python3 staging-rules.py                     # приватные правила → payload'ы
python3 staging-read.py dry                  # цикл без публикации (повтор)
python3 staging-read.py publish              # настоящая публикация в закрытая staging-копия/releases
python3 staging-read.py verify               # счётчики последнего релиза
python3 staging-read.py diagnose             # сверка issue проекта

RANREPORT_RELEASE_DIR=$PWD/закрытая staging-копия/releases python3 -m randreport.web check --db /nonexistent
RANREPORT_BACKUP_PASSPHRASE=… python3 -m randreport.ops.cli backup --db закрытая staging-копия/private.sqlite \
    --out закрытая staging-копия/backups/staging.sqlite.enc --encrypt
RANREPORT_BACKUP_PASSPHRASE=… python3 -m randreport.ops.cli verify-backup --backup закрытая staging-копия/backups/staging.sqlite.enc
RANREPORT_BACKUP_PASSPHRASE=… python3 -m randreport.ops.cli restore --backup закрытая staging-копия/backups/staging.sqlite.enc \
    --db закрытая staging-копия/restored.sqlite
```

## 6. Что осталось (внешнее и требует владельца)

* **Классификация категорий не утверждена.** Приватные правила задают контур
  счетов и календарь, но не классы категорий, поэтому денежный раздел честно
  неполон: одна обезличенная строка «требуют классификации» и метка неполноты.
  Пока стол не запишет карту категорий по устойчивым ID, публичный отчёт не
  сможет показать ни одной содержательной категории.
* **Детализация неопознанного.** Неопознанные суммы публикуются построчно под
  обезличенным ключом (число операций скрыто). Если владелец хочет одну общую
  строку «требуют классификации», это отдельное решение по публичной проекции.
* **Режим сопоставления собраний.** Код поддерживает обе записанные формы
  (`exact` — умолчание, `contains` — владельческая). Для боя нужно явно выбрать
  режим: по умолчанию остаётся осторожное точное совпадение.
* **Внешний контур не включён:** HTTPS/ACME, публичный домен, регистрация
  webhook в Telegram, платный LLM-провайдер и установка боевых служб — не
  выполнялись (условия запуска не наступили). Все локальные проверки шли на
  127.0.0.1, службы staging сняты.

## 7. Что диагностика проекта говорит о реальных данных

После пересборки фактов сверка стола (`diagnose`) находит 281 замечание, из них:
неопознанные категории (28), отсутствующие исторические периоды (3) и **250 групп
«похожих операций без связи пары»** в 33 месяцах — совпадают дата, сумма, счета и
категория, но это разные записи источника (у всех групп уникальные id операций).
Правило проекта такие строки не сливает автоматически: они собираются в одно
замечание уровня месяца (`entity_key` = месяц) и ждут решения человека, а до
решения блокируют уверенную публикацию этого месяца — это ожидаемое поведение
(«ручное „проверено“ не устраняет реальное расхождение автоматически»).
Прежняя ошибка Teamup в списке отсутствует (`source_failed` не воспроизводится,
запись закрыта).

Одна прежняя запись `telegram_history_unavailable` осталась в статусе `open`
(записана до исправления §2.5); новые циклы её не создают.
