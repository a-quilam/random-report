# Закрытый редакционный стол и приёмка публикации

Документ фиксирует закрытый слой редакции (`randreport/admin`): вход через
Telegram, allowlist, сессии и CSRF, проверенность по ревизии, диагностику и
маппинг, модерацию новостей, закрытие неизменяемых версий отчётов и черновик
поста. Источник требований — `docs/REQUIREMENTS.md` §§4, 8, 11, 13; матрица
приёмки — `A01`, `A02`, `R01`, `H01`, плюс сквозной E2E. Публичный слой описан в
`docs/WEB.md`, сбор — в `docs/INGEST.md`, домен — в `docs/DOMAIN.md`.

## 1. Что решено и почему

* **Отдельное WSGI-приложение, без JavaScript и без внешних зависимостей.**
  В окружении нет ни веб-фреймворка, ни библиотеки для JWT (см.
  `docs/TEST_RESULTS_ADMIN.md`), а стол обязан запускаться локально и
  проверяться целиком. Поэтому: `wsgiref`, SSR на f-строках с полным
  экранированием, CSP `default-src 'none'; script-src 'none'`. Формы — обычные
  POST с hidden-полем CSRF: стол работает без JS по построению, а не «по
  возможности».
* **Своя, минимальная проверка подписей (`randreport/admin/jose.py`).**
  Принимаются только асимметричные алгоритмы, которые поддерживает провайдер
  входа — `ES256` (ECDSA P-256) и `RS256` (RSASSA-PKCS1-v1_5 / SHA-256); обе
  реализации перепроверены независимо через `openssl` (см. §8 и
  `docs/TEST_RESULTS_ADMIN.md`). `alg: none` и HMAC-**отклоняются до обращения к
  ключам**: при источнике ключей из JWKS попытка HMAC с подставленным секретом
  недопустима.
* **Одна дверь для входа, два официально поддерживаемых способа.** Основной —
  Telegram OIDC (`authorization code` + PKCE); альтернативный — классический
  Telegram Login с серверной проверкой подписи по HMAC-SHA256 и
  `SHA256(bot_token)`.
* **Доступ — только по списку действующих коммунаров; deny by default.**
  Подтверждённый Telegram-аккаунт вне списка получает отказ и запись в журнал,
  но не сессию. Публичная подписка на канал доступа не даёт.
* **Проверенность хранится по сущности _и_ ревизии.** Отметка «проверено» — не
  флаг: она привязана к хэшу значимых полей и версии правил, поэтому изменение
  источника, классификации, приватности или методики сбрасывает ровно
  затронутые отметки, а не весь стол.
* **Ручная проверка не устраняет расхождение.** Отметка на сущности с открытой
  проблемой записывается как «есть расхождение», а проблема остаётся открытой,
  пока не исчезнет её условие.

## 4. Вход и доступ (§11)

**Поток OIDC.** `GET /admin/login` → редирект на
`authorization_endpoint` с `response_type=code`, `client_id`, `redirect_uri`,
`scope=openid`, `state`, `nonce` и `code_challenge` (S256). Параметры
половины входа (`state`, `nonce`, `code_verifier`, `redirect_uri`, срок)
подписаны HMAC серверным секретом и лежат в HttpOnly-cookie — в URL ничего
чувствительного нет. `GET /admin/callback` меняет код на токены, проверяет
`id_token` по JWKS (подпись, `iss`, `aud`, `exp`, `nbf`, `iat`, `nonce`),
берёт **стабильный Telegram user id (claim `sub`)** и только затем проверяет
список. Неизвестный `kid` вызывает одно обновление JWKS.

**Что отклоняется:** не-HTTPS эндпоинты и redirect URI вне allowlist (для
локального staging разрешён явный `RANREPORT_ALLOW_INSECURE_LOOPBACK=1` на
127.0.0.1); `alg: none`/HMAC; подписи с истёкшим или «будущим» токеном;
несовпадение `state` или `nonce`; подделанная cookie половины входа;
Telegram-аккаунт вне списка; повторный вход отозванного участника.

**Виджет.** `POST /admin/login/widget` принимает подписанный ответ Telegram
Login и проверяет HMAC, свежесть `auth_date` и числовой `id`. Проверенный
аккаунт без строки в `admin_members` всё равно получает отказ: подтверждение
личности ≠ полномочия (в тестах A01 — «username spoof»).

**Сессии.** `Secure; HttpOnly; SameSite=Lax; Path=/admin`, срок 12 часов,
хэш cookie в базе, ротация при повторной выдаче, выход отзывает сессию на
сервере. Проверка состава идёт на **каждом** запросе, а удаление участника
дополнительно немедленно отзывает его сессии, поэтому отзыв действует сразу.
Ограничение частоты: не более 10 неудачных попыток за 15 минут на субъект,
журнал входов ограничен по сроку (30 суток).

**CSRF.** Все изменяющие запросы требуют токен сессии в поле `csrf`
(сравнение постоянным временем) **и** корректные `Origin`/`Referer`, если
браузер их прислал. Отклонённый CSRF попадает в аудит.

**Равные права.** В схеме нет роли: каждый активный коммунар может проверять,
сопоставлять, редактировать летопись и закрывать версии. Последнего участника
удалить нельзя, bootstrap работает только на пустой таблице (ID из
согласованного значения, а не «первый вошедший»), состав меняется через
интерфейс с аудитом.

## 5. Маршруты

| GET | Назначение |
|---|---|
| `/admin/` | обзор: последний запуск, состояние источников, проблемы, неполнота истории, незакрытые периоды |
| `/admin/source/<имя>` | запуски источника, покрытие, последний проверенный снимок, связанные проблемы |
| `/admin/money`, `/admin/money/<tx>` | операции **внутри публичного контура**, карточка, аннотация (денежные поля только для чтения) |
| `/admin/events` | события источника: стабильный ключ, время, тип, публичность, проверка + форма локального сопоставления |
| `/admin/channel` | снимки подписчиков и разрывы |
| `/admin/news` | результаты извлечения, версии, модерация |
| `/admin/reconciliation` | сверка: находки, проблемы, отметки проверки |
| `/admin/publish[/<период>[/v<N>\|/export]]` | список периодов, черновик поста, версии, экспорт |
| `/admin/settings` | контур, категории, типы календаря, источники новостей, донатеры, администраторы, расписание, журнал |
| `/admin/audit`, `/admin/healthz`, `/admin/static/desk.css` | журнал, живость (без данных), оформление |

POST (все с CSRF, все аудируются): `/admin/logout`,
`/admin/actions/{verify,issue/ack,money/annotate,money/edit,mapping/category,
mapping/event,mapping/rollback,news/edit,news/hide,news/restore,news/merge,
publish/save,publish/close,publish/correct,members/add,members/remove,
news-source,donor-alias}`.

Отдельно: `POST /admin/actions/money/edit` **всегда отклоняется** (409) с
объяснением — денежные суммы исправляются только в Zenmoney; допустимы
аннотация и сопоставление категории. Неизвестные сущности и операции вне
публичного контура дают 404 (защита от IDOR): карточка операции вне контура не
открывается даже внутренним пользователем. Список `/admin/money` ограничен
окном (`desk.MONEY_LIMIT`, 200 операций), но карточка `/admin/money/<tx>`
открывается для **любой** операции контура — она ищет операцию по её
идентификатору, поэтому операция старше окна списка доступна и её можно
обратимо исключить или вернуть (`docs/TEST_RESULTS_DESK_WINDOW.md`).

## 6. Диагностика и маппинг (§4, «Сверка»)

Каждая находка несёт: код, важность, объяснение, значимость, источники,
затронутые периоды и объект. Каталог кодов:

`category_unmapped`, `currency_unknown`, `source_changed`, `duplicate_rows`,
`coverage_gap`, `source_unreliable`, `balance_not_reconciling`,
`historical_conflict`, `historical_unresolved`, `historical_gap`.

Жизненный цикл проблемы: `open` → (`acknowledged` — человек написал, что знает)
→ `resolved` только тогда, когда условие перестало обнаруживаться. Отметка
«проверено» **не** закрывает проблему: `checks.verify` на сущности с открытой
проблемой записывает состояние `conflict` и оставляет проблему открытой.

Маппинг — версионируемый: правка категории или подкалендаря создаёт **новую**
версию (`category_mapping_versions`, `event_type_mapping`), прежние остаются,
«откат» тоже создаёт новую версию. Публичный контур (публичные/личные/карантин
счета и категории) виден в настройках; новые счета не включаются автоматически.

## 7. Черновик поста и версии (§3.7, §4)

* **Две плоскости, никогда не смешиваются.** Историческая — опубликованный отчёт
  целого периода (целые рубли, ссылка на публикацию). Живая — выпуск ночного
  сборщика (целые копейки). `plane_for` называет плоскость; если есть обе,
  черновик берёт **одну** (приоритет — опубликованный исторический отчёт), а
  страница прямо сообщает о перекрытии и не складывает числа.
* **Текст.** Пять традиционных разделов + итог/ссылка. Все числа текста
  доказательно взяты из версии: форматированные строки считаются один раз и
  хранятся в снимке (`display`), а `assert_text_faithful` из публичного слоя
  проваливает текст, в котором есть число, отсутствующее в снимке.
* **Закрытие.** Закрытие периода фиксирует неизменяемую версию (v1 из выбранной
  плоскости с провенансом `published`/`recomputed`, автором и временем).
  Повторная запись той же пары `(период, версия)` с другим содержимым
  отклоняется; идентичная — no-op. Исправление — **новая** версия с diff,
  причиной и автором; старые версии доступны по постоянным адресам
  `/reports/<период>/vN`.
* **Периоды.** Метка периода — `YYYY-MM`, `YYYY` или целый диапазон
  `YYYY-MM..YYYY-MM` (групповой отчёт архива, например `2025-01..2025-12`).
  Диапазон — такая же штатная метка снимка, как месяц: индекс периодов и страница
  черновика открываются на ней без ошибки, а нечитаемая метка попадает в список
  как «период не распознан», не роняя панель (проверено `PublishPanelTests`).
* **Готовность.** Статус `ready` не выставляется, пока есть блокираторы: нет
  данных ни из одной плоскости, неизвестны поступления/расходы, период не
  проверен, есть открытая проблема затронутого периода.
* **Экспорт.** Markdown/текст для копирования, без HTML и без внутренних
  идентификаторов. Автопостинг в канал не реализован и не разрешён без
  отдельного решения (в коде отсутствует).
* **Инфографика** из реальных публичных агрегатов (опционально SVG/PNG) не
  реализована — отмечено как остаток в `docs/TEST_RESULTS_ADMIN.md`.

## 8. Проверка подписей: независимая сверка

Обе криптографические примитивные операции проверены не только собственными
тестами, но и сторонним инструментом: синтетическая пара ключей, подпись,
собранный DER/SPKI и публичный ключ в PEM отдаются в `openssl dgst -sha256
-verify` — результат `Verified OK` для ES256 и RS256; испорченное сообщение даёт
`Verification failure`. Это снимает риск «самосогласованной ошибки», когда
верификатор и подписывающая сторона в тестах ошибаются одинаково.

## 9. Связка UI ↔ pipeline ↔ historical/live

* Стол читает **ту же** приватную базу, что и сбор (§§6–10), и публичный слой
  читает релиз, который стол может собрать/закрыть: «Публикация» вызывает
  приватный сборщик, «живая» плоскость страницы — тот же allowlist-релиз.
* Публичный сайт остаётся публичным независимо от ручного закрытия: закрытие
  периода не блокирует ночное обновление (тест R01 «closing does not block the
  live release»).
* Ни один экран стола не суммирует историческую и живую плоскости; E2E
  проверяет, что число из публичного API совпадает с числом в черновике стола, а
  «прототипные» числа из документации не появляются.

## 10. Эксплуатация

Переменные окружения (только серверная сторона, в `.env.example` — плейсхолдеры):
`RANREPORT_DB`, `RANREPORT_ADMIN_SECRET` (секрет подписи cookie; без него стол
не стартует), `TELEGRAM_OIDC_ISSUER`, `TELEGRAM_OIDC_CLIENT_ID`,
`TELEGRAM_OIDC_REDIRECT_URI`, `TELEGRAM_OIDC_REDIRECT_ALLOWLIST`,
`TELEGRAM_AUTH_BOT_TOKEN` (только для виджета), `ADMIN_BOOTSTRAP_TELEGRAM_ID`,
`RANREPORT_RELEASE_DIR`, `RANREPORT_ADMIN_HOST/PORT`.

```
python -m randreport.admin serve --host 127.0.0.1 --port 8098   # по умолчанию только loopback
python -m randreport.admin bootstrap --db … --telegram-id …
python -m randreport.admin member --db … --add|--remove …
python -m randreport.admin sessions --db … [--revoke ID]
python -m randreport.admin history --db …        # наблюдения, конфликты, пробелы
python -m randreport.admin diagnose --db …       # находки и проблемы
python -m randreport.admin close --db … --period YYYY-MM --reason "…"
python -m randreport.admin post --db … --period YYYY-MM [--comment "…"]
```

Стол доступен только на loopback до выбора сервера и TLS. Секреты берутся из
secret store сервисного пользователя, не из аргументов команд и не из git.

## 11. Что осталось внешним

* **Реальные креды Telegram OIDC** (issuer/client_id/redirect, согласованный
  список действующих коммунаров) — без них проверяется только синтетический
  провайдер; интеграция помечена blocked.
* **Приёмка staging и визуальные снимки стола** — задача независимой проверки
  (`t_7b6695ce`).
* **Инфографика** черновика (опционально SVG/PNG) и **правило идентичности
  донатеров** (пока правило не восстановлено, публикуются только общие
  показатели; форма псевдонимов есть).

Боевой стол (карточка t_1b5b08c8): первый администратор внесён в производственную
БД (`admin bootstrap --telegram-id <согласованный ID>`), доступ закрыт
deny-by-default. Вход включён через **Telegram Login widget** штатным bot token
(`TELEGRAM_AUTH_BOT_TOKEN` в `/etc/randreport/admin.env`, отдельного секрета не
заводилось); OIDC подключается отдельно, когда владелец передаст issuer /
client_id / redirect_uri. Проверено на живом столе: согласованный участник
получает сессию, посторонний — `403`, испорченная и устаревшая подпись — `401`,
без сессии — `303`. Дополнительные сведения — `docs/TEST_RESULTS_LAUNCH.md` §3.1.
