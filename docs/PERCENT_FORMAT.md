Решение владельца по задаче `t_7933ce28` (аудит мест вывода процентов).

## 1. Решение

**Выбран вариант 2 — русский вид `3,2 %`, единым правилом на уровне вывода.**

Правило (одно на весь публичный листок):

> Процент печатается как десятичное число с **запятой** в роли десятичного
> разделителя, **ровно с одним** знаком после запятой, затем **один пробел** и
> знак `%`. Неизвестный процент — `не применимо` (в таблице графика —
> `нет данных`), никогда не `0`.

Примеры: `3,2 %`, `96,8 %`, `100,0 %`, `0,0 %`, `99,2 %`, `48,7 %`.

Это то же правило, что уже действует для денег (`90 000,00 ₽`,
`340,59 ₽`): запятая — десятичный разделитель, пробел — разделитель тысяч,
пробел перед знаком единицы.

### Почему вариант 2, а не вариант 1

1. **Деньги на листке уже русские.** `render.rub_from_kopecks` →
   `hints.rub_from_kopecks` печатает `340,59 ₽`. Проценты рядом печатали те
   же доли с точкой (`48.7`). Смесь двух разделителей в одной таблице — это
   дефект, а не стиль.
2. **Стол уже русский.** `admin/reports._coverage_display` (строка 194) давно
   возвращает `f"{str(percent).replace('.', ',')} %"`, то есть `3,2 %`. Публичный
   листок — единственный с точкой.
3. **Документ уже русский.** `docs/TEST_RESULTS_RELEASE.md` §5 (строки 108–109)
   описывает строку «требуют классификации» как `3,2 %` и `96,8 %`, то есть
   документ и страница расходятся именно потому, что страница — выброс.
4. `docs/TEST_RESULTS_*` других модулей и требования владельца (русский листок)
   задают русскую запись как норму.

### Технический аргумент: правило обязано жить в слое вывода, а не в DTO

«Поправить только DTO» **не может** быть единым правилом, потому что не все
напечатанные проценты приходят из DTO:

* таблица категорий печатает `category.share_percent` (строка из DTO), но
* полоса покрытия и её легенда/таблица/`aria`-подпись считаются в
  `render.coverage_bar` из `Decimal`, полученных **прямо в рендере** через
  `render.coverage_segments` → `money.share_percent(...)`, а не из DTO;
* строка `доля … %` на `/events` берёт `metrics['public_share_percent']` (DTO),
  а покрытие в `historical_block`/`report_page` — из `history.coverage_percent`
  (Decimal, вычисленный в момент рендера).

Значит, чисел, которые надо оформить, как минимум три источника, и «единое
правило» реализуется **одной функцией форматирования**, вызываемой в каждом
месте печати. Это и есть «единое правило на уровне DTO/рендера»: правило одно,
применяется на границе показа, а не точечными заменами строк.

## 2. Где правило реализуется (единственная реализация)

1. **`randreport/domain/money.py`** — новая функция рядом с `format_kopecks`:

   ```python
   def format_percent(value: Decimal | int | str | None, *, digits: int = 1) -> str | None:
       """Процент в русском виде листка, напр. ``3,2``; ``None`` остаётся ``None``."""
   ```

   Возвращает **только число** (`"3,2"`, `"100,0"`, `"0,0"`, `"-5,0"`), без
   знака `%` и без слов. Округление — `SHARE_ROUNDING` (`ROUND_HALF_UP`,
   `money.py:16`), дополнение нулём до `digits` знаков. Это **единственное**
   место, где процентное число превращается в текст.

2. **`randreport/web/render.py::percent_text`** (строка 162) — единственная
   обёртка показа на листке:

   ```python
   def percent_text(value: str | Decimal | int | None) -> str:
       rendered = money.format_percent(value)
       return "не применимо" if rendered is None else f"{rendered} %"
   ```

   Принимает и `str` (из DTO), и `Decimal` (из рендера). Все места печати
   вызывают её (напрямую или через уже существующие вызовы `percent_text`).

3. **`randreport/web/render.py::_percent_chart`** (строка 177) — тот же формат для
   долей, которые не только печатаются, но и рисуются (полоса покрытия):

   ```python
   def _percent_chart(value: str | Decimal | int | None) -> str:
       rendered = format_percent(value)
       return "нет данных" if rendered is None else f"{rendered} %"
   ```

   Различие с `percent_text` ровно одно и оно из правила §1: у графика неизвестная
   доля — «нет данных», у остального текста — «не применимо». Число в обоих случаях
   оформляет `money.format_percent`, поэтому «два слова» не превращаются в «два
   формата»: `coverage_bar` берёт `_percent_chart` для `aria`-подписи и таблицы
   графика, `percent_text` — для `headline`, `figcaption` и легенды.

4. **Не менять** `minibar` и `coverage_bar` геометрию: ширины прямоугольников
   (`viewBox`-единицы, `render.py:479`, `:531`, `:538`) и `_decimal_or_none`
   остаются числовыми. Печатный текст тех же чисел идёт через `percent_text`,
   геометрия — нет. Если подставить русскую строку в `width="{…}"`, полоса
   сломается (атрибут SVG должен остаться `48.7`, а не `48,7`).

## 5. Чек-лист поверхностей (выполнено, снято с живого адреса)

Требование к каждой поверхности: денежные суммы и проценты — по одному правилу;
вхождений `[0-9]+\.[0-9]+ %` нет, `[0-9]+,[0-9]+ %` есть там, где печатается доля.
Столбец «было» — те же числа, как их печатал листок до правки: с точкой и **без
знака процента** (так они же выглядят в машинном слое, §3). Полный сырой HTML до
правки — в приложении карточки `t_7933ce28` (`raw/*.html`, `percent_evidence.txt`).

Проверено на боевом `https://rand.185.121.13.113.sslip.io` (тело побайтово совпадает
с сырым ответом `127.0.0.1:8099`): вхождений `[0-9]+\.[0-9]+ %` — **0** на всех
поверхностях, значений с запятой — 44 (25 + 16 + 1 + 2). Геометрия осталась
числовой: в том же HTML `width="3.2"` и `width="96.8"`, то есть точка в SVG-атрибуте
на запятую не заменена (правило §3).

То же на других периодах (не только на периоде по умолчанию): `/?period=2025` — 18
значений, `/money?period=2025` — 32 значения, `[0-9]+\.[0-9]+ %` — 0; архив

обеих сумм).

Проверка отсутствия «смеси» — регулярка по сырому HTML каждой поверхности и по
текстам документов:

```bash
grep -nE '[0-9]+\.[0-9]+ %' <страница>   # должно быть пусто
grep -nE '[0-9]+,[0-9]+ %' <страница>   # должно находить доли
grep -rnE '[0-9]+\.[0-9]+ ?%' docs/      # должно быть пусто (см. §9)
```

горизонтальной прокрутки нет на 1440/390/320
(`document.documentElement.scrollWidth <= clientWidth`).

## 6. Регрессионный тест (выполнен в `t_31a3ef88`)

Один тест на собранном синтетическом релизе (`tests/test_web_leaflet_composition.py`,
класс с `PublicSite`) и/или на живых URL:

1. **Нет точки как разделителя процентов.** Для каждой из страниц
   `/`, `/money`, `/support`, `/events`, `/reports`, `/reports/<год>`
   `re.search(r"\d+\.\d+\s*%", html)` возвращает `None`.
2. **Есть запятая.** Хотя бы на `/money` и `/` `re.search(r"\d+,\d+\s*%", html)`

## 9. Как проверять запись процентов (документы и страницы)

**Страницы.** Для каждой поверхности — сырой HTML и обе регулярки (§5). Критерий
приёмки: `[0-9]+\.[0-9]+ %` не находит ничего, `[0-9]+,[0-9]+ %` находит доли.

**Документы.** Ни один пример процента в `docs/` не записан по правилу, отличному
от принятого: числа с точкой, за которым сразу идёт знак `%`, в документах нет.

```bash
grep -rnE '[0-9]+\.[0-9]+ ?%' docs/    # пусто
grep -rnE '[0-9]+,[0-9]+ ?%' docs/      # примеры принятого правила
```

Допустимая десятичная точка в `docs/` только одна — **числа машинного слоя** (§3:
`share_percent` в DTO/`releases.json`/CSV, `width="96.8"` в SVG). Такие числа
записаны **без знака `%`**, поэтому под эту регулярку не попадают — ровно как и
числа в столбце «было» (§5, §7, §8). Если нужен пример того, как выглядело **до**
правки, он тоже пишется числом без `%` и рядом помечается «было»/«до правки»:
иначе документ сам начинает показывать правило, которого на странице нет.
