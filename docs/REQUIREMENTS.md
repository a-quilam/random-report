## 2. Обязательные продуктовые решения (не пересматривать)

| Параметр | Решение |
|---|---|
| Продукт | Постоянный общедоступный сайт с закрытой редакционной панелью |
| Финансовый источник | API отдельного, уже полностью настроенного аккаунта РанДома в Zenmoney. Google Sheets не является источником текущих финансов |
| Календарь | Teamup Calendar (teamup.com, не одноимённый сервис goteamup.com) |
| Канал | Публичный Telegram-канал РанДома; число подписчиков и публичные посты |
| Синхронизация | Один суточный цикл, старт в 03:00 Europe/Moscow; сразу публиковать успешное безопасное обновление с признаком проверки. Не опрашивать источники каждые 5 мин/час |
| История | С начала существования по сохранившимся отчётам и данным — агрегированно, с реальным покрытием; с момента начала разработки/подключения источников — детально. Не считать дату первой записи датой основания |
| Фактические события | Есть в календаре на момент успешной синхронизации и уже завершилось (`end <= cutoff`) — считаем состоявшимся. Без обязательного подтверждения организатором, посещаемости или ручного статуса. Будущее и продолжающееся исключаются |
| Закрытые события | Включать агрегированно в общую статистику, без названий, дат отдельных событий, точных часов, участников, описаний, организаторов, ссылок |
| Финансовая прозрачность | Все денежные потоки публичного пространства в суммах по категориям; также текущий суммарный остаток. Не публиковать отдельные операции, исходные комментарии, счета, платёжные реквизиты, личные расходы или взносы поимённо |
| Проверка | Оперативные данные появляются до ручной проверки, затем доступны отметки проверки; исправления видны в истории |
| Новости | Автоматически извлекать из публичных постов Telegram с помощью ИИ; без обязательного ручного согласования каждого результата |
| Топ-донатеры | Сохранить существующую традицию/методику публикаций, а не придумать новую. Пока точные правила не извлечены, раздел показывать агрегированно; исторические опубликованные записи сохранять |
| Админка | Все действующие коммунары через авторизацию Telegram, равный доступ к редакционной работе; не любой подписчик |
| Исправление финансов | Только в Zenmoney. Сайт не записывает финансовые операции в источник и не имеет локальных денежных «поправок» |
| Валюта | Фактические номинальные рубли, без инфляционной поправки |
| Размещение | Выбор в ходе разработки: сравнить текущие ресурсы и доступные варианты, не считать заранее утверждённым конкретный сервер или домен |
| Отчёты | Архив постоянных ссылок и версий, месячные Telegram-черновики, экспорт публичных агрегатов |

Термин «в реальном времени» означает ежедневно обновляемую отчётность, а не стриминг банковских транзакций. Отметка времени — честная. Автоматическое обновление сайта не гарантирует, что все банковские операции уже внесены в Zenmoney.

## 3. Публичный интерфейс

Общее: посетитель не регистрируется. На всех аналитических страницах заметный период, дата последней успешной синхронизации конкретного источника, состояние проверки/полноты. Навигация сохраняет период в URL. Текущий календарный месяц по МСК по умолчанию; предыдущий месяц, текущий год, предыдущие годы, произвольный период, всё время. Для исторических агрегатов ограничивать детализацию доступными полными периодами. Не интерполировать месяцы, не распределять годовую сумму пропорционально; неизвестное показывать «нет данных», а подтверждённое отсутствие — 0. Сравнение с прошлым месяцем, тем же месяцем прошлого года, год к году; для неполного текущего периода показывать «по состоянию на» и сопоставимый elapsed-период только при наличии данных; не сравнивать неполный месяц с полным молча.

### 3.1 Главная `/`

Первый экран: название «А дорог ли РанДом?», объяснение модели, переключатель периода, индикатор покрытия расходов поступлениями от деятельности и донатами; разбивка покрытия по источникам, непокрытая часть; расходы и поступления в рублях; фактический вклад коммунаров отдельной строкой, если достоверно учтён. Неотождествлять его с расчётной непокрытой частью. Дальше число состоявшихся мероприятий, доля публичных, число подписчиков и изменение за период, свежие новости, переходы к денежной статистике, календарю, поддержке и методологии. Баланс — показатель финансовой страницы, не заглавный показатель успешности. Публичная ссылка «Как поддержать» ведёт только на проверенные реквизиты/ссылки из действующих публичных материалов, не на выдуманную форму оплаты. Визуальный ориентир — понятная полоса 100% покрытия с сегментами донаты, возмещения/ивенты, прочее, недостающая часть; при >100% не рисовать отрицательные сегменты и не обрезать реальное значение процента.

### 3.2 Деньги `/money`

Отдельные блоки: расходы, компенсация (донаты + внешние поступления от деятельности), фактические взносы/субсидирование коммунарами, разница между затратами и компенсацией, остаток средств на дату последнего успешного финансового снимка. Поступления и расходы — список всех фактически имеющихся публичных категорий, суммы и доли; отдельные строки «Доля с ивента», «Склад», «Занятие подвала», «Книга», если применимы; никаких ненужных слияний или хардкода категорий. График динамики покрытий и номинальных расходов/поступлений по месяцам/годам; вклад каждого типа финансирования; отдельно видимые неопознанные суммы, не спрятанные в «прочем». Если известны обязательства, показать их отдельно и с датой (не вводить оценки обязательств из баланса). Детали публичной строки — определение категории, агрегаты по допустимым периодам, расшифровка методологии и источника, без операций. CSV только по категориям и полным безопасным временным корзинам, без transaction_id/account_id/контрагентов и дневных сумм. См. раздел 6 о недопустимости восстановления отдельных операций через фильтры.

### 3.3 Мероприятия `/events`

Календарь состоявшихся публичных событий, список, фильтрация по месяцу/году, типу. Для публичного события название, дата, допустимое описание, опубликованный анонс/фото при наличии и разрешении. Архив открытых по записи — также публичный, но не показывать записи участников. В общей статистике показывать пять традиционных типов: открытые, открытые по предварительной записи, закрытые, внутренние собрания, репетиции/подготовка. Дополнительные форматы (лекция, кино, игры и т.д.) — вторичная аналитика только при достаточной надёжности классификации. Закрытое событие не попадает в календарную сетку даже анонимной точкой; только агрегаты безопасного периода. Дни с событиями/часы загрузки/организаторы и посещаемость — опциональные метрики, только если источник даёт нужные данные, без раскрытия закрытого расписания. Не считать количество мероприятий числом участников и не выдавать часы брони за социальный эффект. Исторические периоды с неизвестными событиями не содержат фиктивного списка.

### 3.4 Сообщество `/community`

Число подписчиков последнего доступного снимка, изменение между фактическими точками начала/конца выбранного периода, график динамики с пробелами. В историческом архиве — только датированные подтверждённые точки; никакой искусственной ежедневной ретрополяции. Если есть надёжная статистика публикаций/охватов, показывать её отдельно с определением; иначе не выдумывать. Ссылка на канал.

### 3.5 Поддержка `/support`

Сумма донатов и число пожертвований (не число уникальных людей), тренд, как поддержать. Топ-донатеры исключительно согласно уже существующей практике отчётов: сначала восстановить правила по оригинальным постам (кто входит, период, что именно ранжируется — сумма или иной критерий, отображаемое имя, анонимность, размер списка, возможная публикация сумм). Не предполагать, что «донат от организатора», «впис», возврат, возмещение или «пополнение» — донат. Не сопоставлять людей по банковским комментариям, телефону, ФИО или LLM. Пока нет надёжного правила идентичности и публичного права на имя — показывать только общие показатели и ранее публично названных людей в соответствующих архивных отчётах. Новые имена — только явно разрешённые публичные идентификаторы/псевдонимы, с возможностью исключения из будущих выдач. Суммы по людям только если это часть проверенной прежней методики и разрешены. Не требуется вводить новые банковские персональные данные.

### 3.6 Летопись `/chronicle`

Новости — не копия всех анонсов. События развития: ремонт, приобретения, организационные изменения, инициативы, значимые результаты, трудности, начало/завершение проектов, новые форматы и важные решения, если об этом уже сказано публично. Хронологические карточки: дата публичного сообщения или достоверная дата новости, короткий заголовок, краткое изложение, категория, ссылка на 1+ публичных первоисточников, отметка автоматической обработки, редактирования/проверки. Объединять несколько публикаций про одно достижение только с сохранением источников. Скрывать обычные анонсы, повторы, домыслы, закрытые сведения. Подробности LLM в разделе 8.

### 3.7 Архив `/reports`, `/reports/YYYY-MM`, `/reports/YYYY`

Отчёты за каждый доступный период. Восстановленные исторические агрегаты с provenance и полнотой. Для месяца сохранять исходный опубликованный текст (если найден), его ссылку, и структурированный снимок. Для нового месяца оперативная версия формируется автоматически; после ручного закрытия — неизменяемый снимок с номером версии. При изменениях старых данных оперативный слой пересчитывается; фиксированный снимок не перезаписывать, в отчёте видны исправления, автор/дата во внутреннем аудите, публично — что и почему было скорректировано без раскрытия транзакций. Старые версии доступны по постоянному URL. Годовой отчёт на той же методике, не самостоятельная формула из отдельных категорий. Групповой исторический отчёт за апрель–август — единый период, не пять искусственных месячных отчётов.

### 3.8 Методология `/methodology`

Что считается доходом/компенсацией, субсидией, расходом, трансфертом, балансом, событием. Причины отсутствия истории и статус проверки. Формулы, дата и версия методологии, соответствие категорий, различия исторических и текущих данных, правила округления, время обновления. Пояснение об устройстве проекта: некоммерческая по цели общественная деятельность, коммунары покрывают затраты. Ссылка на проверяемые публичные источники и CSV агрегатов. Формулировки доступным языком, без «должны заработать».

### 3.9 Дизайн и доступность

Редакционная эстетика самиздата, зин-культуры, небольшого независимого культурного пространства. Бумажный фон, тёмный текст, приглушённые фиолетовый/розовый/зелёный акценты, крупная типографика, аккуратные графики; допустимы шероховатости в декоративных элементах, не в читаемости. Не корпоративный SaaS, не стеклянные карточки, не безликий банковский интерфейс. Оригинальный логотип, реальные разрешённые фотографии, минимум генеративного декора. Условные референсные числа не попадут в production. Не делать изображение вместо интерактивных графиков. Мобильная вёрстка 360px+, таблицы скроллируются без поломки страницы; клавиатурное управление, фокус, screen reader, контраст WCAG AA, текстовые альтернативы графикам, без обозначения статусов одним цветом. Быстрая загрузка, отсутствие внешних трекеров по умолчанию, SSR/static export, стабильные URL. Примеры копирайта: «Сколько стоит наш подвал?», «Что мы на эти деньги делаем?», «Сначала считаем, потом хвастаемся». Юмор мягкий. Не использовать «прибыль» для остатка. Пороговые фразы опциональны и не должны подменять объяснение цифр.

## 4. Административная панель

Редакционный стол закрыт Telegram-авторизацией. Все действующие коммунары имеют равный доступ к проверке, сопоставлению категорий, редактированию летописи, подготовке отчётов. Из прежнего локального прототипа переносим принципы, а не хранилище браузера.

- Обзор: последний ночной запуск, состояние каждого источника, число проблем, проверенность, данные, требующие решений, незакрытые периоды. Переход к источнику и деталям проблем.
- Деньги: таблица исходных операций в пределах разрешённого публичного контура во внутренней базе, поиск/фильтры, дата, сумма, тип, категория и происхождение, карточка строки и отметка проверки. Денежные поля только для чтения. Исправлять в приложении Zenmoney. Не создавать локальных денежных корректировок; разрешены только сопоставление категорий/счетов и аннотации. Не выводить сверх необходимого банковские подробности даже во внутреннем UI.
- События: источник, стабильный идентификатор, время, тип, признак публичности, проверка; исправление события в Teamup, изменения локального маппинга публичности и категорий с аудитом. Никакого второго календаря. Фактическое прошлое не ставить на обязательное ручное подтверждение.
- Канал: снимки и пропуски, ссылки на источники, проверка исторических точек. Новости: отредактировать/объединить/скрыть неверный результат ИИ, восстановить исправленный текст, аудит. Донатеры: утверждённая методика и безопасные публичные имена; ручное объединение дублей только с надёжным основанием, не по догадке.
- Сверка: годовая сумма месяцев vs итог, известные исторические расхождения, пропуски, новые категории, незамапленные операции, проблемы валюты, отменённые или изменённые источником, дубли, несовместимые периоды, несходящееся изменение остатков. Для каждой: объяснение, источники, затронутые периоды, значимость, статус и комментарий. Ручное «проверено» не устраняет реальное расхождение автоматически.
- Публикация: превью месячного поста в формате традиционных пяти разделов + итог/ссылка, ручной комментарий, статус готовности, копирование Markdown/текста, безопасный снимок и экспорт. Сайт после ночной синхронизации публичен, ручное закрытие не блокирует обновление. Автоматически постить в канал не требуется и не разрешено без отдельного решения. Инфографика — генерируемая из реальных публичных агрегатов, а не нарисованные ИИ числа; опционально SVG/PNG.
- Настройки: карта публичного контура, категории по ID, типы Teamup, правило донатеров, разрешённые источники новостей, списки администраторов, расписание и статус. Журнал изменений и обратимости настроек; аудит без секретов. Не разрешать произвольный HTML/JS в редакторе.

Проверенность хранится по сущности и ревизии (hash нормализованных значимых полей + версия правил). При изменении источника, классификации, приватности или методики затронутые отметки сбрасываются автоматически; несвязанные остаются. Можно проверять отдельную строку, категорию/раздел и период только при видимом наборе данных и версии. Различать «оперативные», «проверено», «есть расхождение», «нет данных», «устарели». Свежесть и проверенность — независимые признаки. Не давать проверенному вчера значению зелёный статус после изменения сегодня. Публичная сводка не раскрывает, кто и какую операцию проверял.

## 5. Архитектура: рекомендованная, не догма

Один небольшой репозиторий, модульный монолит. Рекомендация: Python 3.12+ / FastAPI, SQLite (WAL, миграции, транзакционные снапшоты), SSR через Jinja/HTMX или Astro + TypeScript, лёгкие SVG/браузерные графики, Caddy/Nginx/TLS, systemd timer или эквивалент. Выбор между SSR и Astro обосновать; не усложнять двумя сервисами ради моды. Public API/статика читают только построенную allowlist-проекцию, admin требует проверенной сессии. При возможности изолировать публичные данные в отдельный read-only SQLite/JSON snapshot, веб-процесс не имеет доступа к приватному журналу/секретам. Публикация единым атомарным переключением версии. Никакого ORM/API, сериализующего произвольные сырые сущности наружу. Не привязывать систему к конкретному VPS до оценки. Никаких Kubernetes, очередей и LLM на пути загрузки страницы без необходимости. Нет зависимости от постоянной работоспособности Hermes: сайт и рутинная синхронизация автономны, Hermes обслуживает и развивает.

Схема:

```
Zenmoney / Teamup Calendar / Telegram
    → адаптеры (read-only) → staging + курсоры + локальный архив
    → нормализованные факты + маппинги → проверки/расчеты → публичная проекция
    → атомарный релиз → публичный сайт + CSV + отчёты
                              ↘ закрытая редакционная панель
Публичные Telegram-посты → дневной пакет → LLM-extractor → валидатор → летопись
```

Пример модулей: `connectors/zenmoney`, `connectors/teamup`, `connectors/telegram`, `domain/finance`, `domain/events`, `domain/news`, `history`, `projection`, `web/public`, `web/admin`, `ops`, `tests`. Секреты только из environment/secret store с правами процесса. `.env.example` содержит placeholders. Ни одного токена, приватной ссылки Teamup, сессии Telegram или реального сырого дампа в репозитории (включая private GitHub), тестовых фикстурах, логах и CI.

## 6. Zenmoney: финансовая модель и коннектор

### 6.1 Интеграция

Использовать официальный API аккаунта РанДома (не аккаунт пользователя в текущем ChatGPT, не личный кошелёк). Исследовать имеющийся способ OAuth/выдачи токена и минимальные разрешения; если API не предоставляет отдельный read-only scope, реализовать технический запрет отправки изменений и отделить credential от UI. Начальный full diff, затем incremental по `serverTimestamp`, `currentClientTimestamp`; API `/v8/diff/` возвращает изменения и записи удаления. Точная схема и URL — проверить официальную документацию в момент реализации, не полагаться на неизменность версии. См. `HISTORY.md` (технические ссылки). Клиент read-only: отправляет метки синхронизации и допустимые read-поля, никогда массивы изменения транзакций/счетов/категорий или deletion. Не интерпретировать наличие API доступа как разрешение менять учёт.

Сохранить стабильные ID, связи счетов и категорий, тип счета/валюту, даты, рублёвые суммы, связь доходной/расходной стороны, флаг удаления, исходную ревизию, время получения. Хранить только минимум полей для расчётов и диагностики. Обработать обновление, удаление, повторную доставку, истёкший токен, повтор после сбоя, начальную загрузку, полную пересверку при потерянном курсоре; транзакционно обновлять факты и курсор только после успешной обработки всего ответа. Снимки балансов с датой, валюта и границы scope. Не использовать текущие account balances для исторического баланса при отсутствии корректного снимка. Сервис не должен обращаться к банковским API сам: Zenmoney источник учёта.

### 6.2 Граница публичного пространства

Даже отдельный аккаунт не отменяет проверку scope: инспектировать реальные категории, счета, переводы и учет расходов/взносов; создать версионированный маппинг по устойчивым ID счетов и категорий. Все публичные финансы должны попасть в модель; личные/жилые/несвязанные — нет. Исторический Excel явно содержит общий бюджет коммуны и жилые траты. Не подменять публичный контур этим полным бюджетом. Если счет или категория смешанного назначения, классифицировать по надёжным тегам/сторонам, иначе выделять в карантин «объём, граница которого уточняется», не публикуя личные средства. После первичной сверки сохранять mapping в БД; имя — display label, не ключ. Общая сумма категорий «требуют классификации» публична только для операций заведомо публичного контура. Неопределённость самого контура — внутренняя проблема с публичным предупреждением о неполноте, без суммы потенциально приватных средств. Новые счета не включать автоматически, пока не установлена их область. Новые категории на уже определённом публичном контуре учесть в общей денежной сверке и безопасном агрегате, не приписывать автоматически к компенсации или субсидии. Если исходное имя новой категории содержит имя/реквизиты, использовать безопасное отображаемое название до проверки.

### 6.3 Классы финансовых потоков

Различать не только приход и расход, но экономический смысл. Внутренняя нормализованная enum: `external_compensation`, `commune_subsidy`, `operating_expense`, `expense_refund`, `compensation_refund`, `financing_in`, `financing_out`, `internal_transfer`, `balance_adjustment`, `unclassified`; классификация зависит от реального способа учета и пары счетов. Возможность детального подтипа. Экономические классы и безопасные публичные категории не зависят от регистра исторических названий. Старые «Донат»/«донат» и «Награда»/«награда» не считать отдельными в нормализованном историческом словаре, но исходное написание сохранить. Не считать `Плюсовые` автоматически «доходом подвала». `Впис`, `Пополнение`, проценты, «Благо-сть за аренду», займы и возвраты требуют анализа контекста, не безусловная компенсация. Исторический «Лофт» — прежняя категория возмещений организаторов; не утверждать, что такой ID есть в Zenmoney.

- Компенсация: донаты, фактические возмещения организаторов, доля с ивентов, склад, занятие подвала, книги, напитки и прочие доказанные поступления от деятельности; суммы возвратов этой выручки уменьшают соответствующее поступление.
- Субсидия: реально направленные средства коммунаров на содержание публичного пространства. Прямо оплаченные коммунарами расходы, если они отражены в учёте, учитывать по согласованному способу: одна расходная операция и один вклад/источник финансирования; не считать сначала прямую оплату, затем возмещение той же покупки как второй расход. Не считать взносы на жилую часть субсидией публичного пространства. Если источника для фактической субсидии нет, показатель неизвестен; вычисленный дефицит — не факт взноса.
- Расход: аренда/доля аренды публичного пространства, коммунальные/хозяйственные, оборудование, ремонт, расходники, на ивенты и другие фактические расходы публичного контура. Возврат покупки уменьшает расход, не становится внешней компенсацией. Коммунальные и аренда могут быть совместными: использовать только реальную подтверждённую долю, не выдумывать проценты распределения. При недоступной доле — пометка неполноты.
- Переводы внутри контура (включая между картой и кассой, накоплением и расходным счетом) не доход/расход и не влияют на консолидированный остаток. Перевод через границу — классифицировать по назначению и источникам, не считать внешним доходом только потому что технически есть incoming. Парные движения не дублировать. Наличность и возвраты займа/кредита, залоги, погашения долга, корректировки баланса и противоположные стороны — отдельный экономический поток; проценты явно классифицировать по назначению. Не включать плановые операции в фактические суммы. Отдельно записать комиссию на перевод при наличии, как реальный расход.

### 6.4 Формулы

Все суммы в копейках целым числом или Decimal с заданным округлением; исключить float для расчета. Дата учёта — фактическая дата операции в согласованной TZ; не дата последнего редактирования. Для периода P:

```
E = gross_operating_expenses - expense_refunds        # расходы, положительная величина
C = external_compensation - compensation_refunds     # компенсация
S = actual_commune_subsidy_net                        # фактический вклад (nullable)
D = E - C                                            # непокрытая часть ДО субсидии, signed
coverage = 100 * C / E   if E > 0 and inputs complete else null
shortfall = max(D, 0)    if D known else null
excess = max(-D, 0)      if D known else null
operating_result_before_subsidy = C - E
operating_result_after_subsidy = C + S - E            # nullable if S missing
B = sum(confirmed public liquid-account balances)    # snapshot as of sync; not profit
```

Финансирование/возвраты займов и корректировки не смешивать с operating result; отдельно показывать, как объясняется изменение баланса. `cash_delta = closing_balance − opening_balance` только при известных корректных снимках, и оно может отличаться от результата деятельности из-за несвязанных финансовых потоков, прямых оплат, времени учёта. Баланс — фактически учтённые денежные средства в кассе/на публичных счетах; не «свободные деньги», не прибыль, не сумма кредитного лимита. Долги/обязательства/неликвидные активы отдельно, не прибавлять к ликвидным деньгам. Если подтверждённый остаток 0 — показывать 0. Если счёт с неизвестной принадлежностью/валютой — показывать состояние неполноты. Не автоматически считать отрицательный D резервом или свободными деньгами. При `E = 0` — процент «не применимо», а не 0/100 или infinity. Если E < 0 из-за возвратов, показать фактическую сумму и объяснение, процент не применим. Неполные категории — не выдавать точный coverage за окончательный (пометка неполноты, при необходимости null). Суммы фактически внесённых взносов не выводить на основании дефицита. Показатели 100% и выше валидны, но не означают, что долгов нет. Годовой coverage — отношение годовых сумм, не среднее месячных процентов; рост подписчиков — разница точек, не сумма с пропусками. Стоимость на событие — E / количество состоявшихся событий при известных, сопоставимых периодах, подписать «условные расходы на одно событие» (не цена конкретного мероприятия).

Пример теста: E=100000, C=60000, S=40000. Покрытие 60%, непокрытая часть 40000, результат после субсидии 0. Текущий баланс неизвестен из этих данных. При E=100000,C=110000,S=0 coverage=110%, excess=10000, но баланс неизвестен. При E=100000,C=60000,S=null — вклад и после-субсидийный результат null. Результат до субсидии −40000 известен.

### 6.5 Сверка

Месяц/год/всё время — один query/одна функция, единая карта категорий. Сверять суммы всех категорий с нормализованным потоком (включая отдельные `unclassified`, `financing`, adjustment), сумму месяцев с годом при совместимом полном покрытии. Историческая сверка имеет свои provenance и не автоматически считается текущей ошибкой. Не исправлять старое опубликованное значение задним числом без версии. Новая категория должна попасть в месячный и годовой расчёт без изменения формулы. Суммы показывать в номинальных рублях; если фактические нерублёвые операции встретятся, использовать фактическую рублёвую оценку источника, иначе пометить отсутствие курса, не пересчитывать задним числом текущим курсом.

### 6.6 Конфиденциальность агрегатов

Публичная детализация финансов — категории, месяц/год и согласованные агрегаты, произвольные даты только целыми разрешёнными корзинами. Не выдавать API фильтр по одной операции, точному дню, счёту или человеку. Даже категорийный агрегат с единственной операцией или последовательные ежедневные снимки могут косвенно раскрывать сумму; это компромисс заданной прозрачности. Минимизировать риск: не показывать число операций для мелких чувствительных категорий, не выдавать дневные финансовые CSV/версии с диффом транзакций, исключать идентификаторы/описания. Действительно чувствительные публичные категории не именовать персонально. В приватном проектном обсуждении явно указать остаточный риск вычитания суточных сумм; не скрывать общие суммы по присылаемым категориям без причины. Публичный баланс только суммарный, без breakdown по счетам.

## 7. Teamup: события и сохранение истории

Источник — Teamup Calendar `api.teamup.com`; уточнить документированный API key и read-only календарный доступ (не публично раздавать секретный calendar key). Первая загрузка всех доступных прошлых событий с реальным диапазоном, дальнейшие суточные изменения и достаточный overlapping window; сверять API-specific `modifiedSince`, сроки хранения changelog, recurrence semantics, документированный limit и pagination. При отсутствии надёжного incremental — запросить окна по датам с достаточной глубиной и проверять изменения, не стирать локальную историю. История Teamup на текущем тарифе ранее уже утрачена: PDF 2025 неполон, пользователь сообщал о сохранившейся части ноября и декабря. Данные после старта разработки сохранять в своей БД навсегда с резервным копированием. Автоматически не удалять локальные завершённые события при исчезновении из-за retention. Если календарь вернул явное удаление/отмену, удалить из оперативной статистики, сохранив внутреннюю ревизию; если в календаре на момент синка существует завершённая запись — считается состоявшейся. Не вводить произвольные «подтверждения», обязательные признаки посещаемости и LLM-отбор. Если название содержит «отмена», но запись остаётся в календаре, следовать согласованному правилу пользователя, а не семантической догадке; возможную проблему показать админу. Не считать системные не-события только после проверки структуры календаря и маппинга, не исключать собрания и подготовку.

Хранить каждое occurrence по устойчивому ID календаря + ID экземпляра, series ID и нормализованному времени при необходимости; одна запись, размещенная в нескольких subcalendar, считается один раз. Повторяющиеся события считаются по каждому экземпляру, а не по правилу recurrence. Редактирование и перенос не создают искусственные дубли. Плановые события можно временно сохранять для обнаружения переносов/удалений, но не публиковать/считать. TZ Europe/Moscow; нормализовать UTC плюс локальный день (период события по началу, факт по концу; ночное событие не засчитывается дважды; all-day exclusive end сверить с API). Состоявшееся: `end <= run_cutoff` и имеется действительная запись, которую источник вернул либо архивировал до retention. Длительность неизвестна — не выдумывать. Календарь с неизвестным типом — учитывать в total и «тип не указан», не считать автоматически открытым. Тип и приватность настраиваются по устойчивым subcalendar ID/полям/проверенному mapping, не по цвету страницы или названию в одиночку. Конфликтующие календари — приоритет приватности; закрытое/внутреннее всегда агрегированно; повторная классификация пересчитывает статистику. Для открытого по записи не показывать форму регистрации уже прошедшего события как актуальную.

Закрытые данные: публичная выдача и статические файлы не содержат идентификаторов закрытых событий, дат/часов/длительностей, названий, людей, ссылок, заметок, точек на heatmap. Публичный общий счётчик включит их; месячный/годовой агрегат по типам. Не выдавать дневные totals всех событий в сочетании с публичным календарём (иначе дата закрытого восстанавливается вычитанием). Не отдавать произвольные периоды, которые изолируют закрытое событие. Учитывать остаточный риск суточного изменения месячного счётчика — это неизбежный компромисс выбранной публикации агрегатов, не усугублять деталями. Исторический календарь PDF не публиковать; не реконструировать реальные события из наложенных текстов PDF как достоверную базу. Использовать отчёты/сохранившийся календарь, явно различать детализацию и покрытие.

## 8. Telegram и ИИ

Снимок `getChatMemberCount` один раз в 03:00 (дневной снимок), источник `channel_id` проверен, авторизация ботом/официальным API. Ошибка не равна 0. При повторе в тот же день не дублировать снимок без новой ревизии. Историю числа подписчиков Bot API задним числом не выдаёт: взять только реальные зарегистрированные значения или датированные отчёты. Сохранять время получения отдельно от даты периода. Прирост по границам или с указанием фактических точек, при неизвестном начале — null.

**Новости:** каждый ночной цикл прочитать новые и изменённые публичные посты после устойчивого курсора, иметь механизм надежного backfill/восстановления пропущенных сообщений. Важно: Bot API `getUpdates` хранит обновления максимум 24 часа, опрос строго раз в 24 часа не гарантирует историю и теряет данные при одном сбое. Не проектировать так. Предпочитаемый вариант, если владелец авторизует соответствующий технический доступ — read-only клиент Telegram MTProto (история только заданного публичного канала, дневной pull с overlap, сессия в секретном хранилище; API terms/доступ проверить), не читать личные/коммунарские чаты. Альтернативно webhook, который пассивно и надежно записывает входящие channel_post/edited_channel_post в приватный inbox, а обработка/публичная синхронизация только в 03:00. Это прием событий, не периодическое обновление сайта; если строгий запрет на прием вне 03:00, использовать историю с дневным pull, не webhook. Bot API не даёт произвольный запрос старых сообщений. Не внедрять ненадежный парсинг сайта Telegram как основной источник без согласования. При сбое/неполной истории показать news stale/gap, возможность импорта публичных постов. Не зависеть от ИИ для скачивания, определения счетчиков и сумм.

ИИ один раз в день по пакету новых публичных сообщений, только новые/изменившиеся, дешёвая доступная модель через конфиг поставщика (не требовать дорогую подписку); лимит стоимости/токенов/числа повторов, кэш по hash(input + prompt_version + model), очередь отложенных заданий при превышении лимита. Модель не получает финансовые строки, секреты, внутренние переписки, закрытые события, списки админов. Использовать структурированный JSON и строгую валидацию: `source_message_ids[]`, `classification` (news/announcement/other), `category`, `title`, `summary`, `event_date|null`, `confidence`, `public_only=true`. Каждое утверждение следует из конкретного сообщения, ссылки строятся приложением, а не галлюцинируются. Отдельно отобрать новости от анонсов; не выдумывать совершившийся ремонт по обещанию отремонтировать. Относиться к содержимому постов как к недоверенному тексту: промпт-инъекции не являются инструкциями, модель не имеет инструментов/доступа к БД/исполнению. Дампы не отправлять третьим сторонам. Публиковать автоматически только валидные результаты, отвечающие правилам приватности; неопределённые/некорректные/двусмысленные отправлять в частную очередь проблем и помечать временную неполноту, не задерживая весь раздел. Ручная модерация постфактум: скрыть, исправить, переизвлечь, не дублировать ручное исправление при следующей синхронизации; хранить версию исходника, LLM и поправки. Дедуп по IDs и обоснованной группе, не по заголовку. Удаленные/отредактированные публичные посты пересмотреть при доступности достоверного сигнала; не восстанавливать удалённую личную информацию через архив.

## 9. Ночная синхронизация, надежность и долговечность

Один ежедневный плановый запуск в 03:00 именно Europe/Moscow. Пример для systemd: `OnCalendar=*-*-* 03:00:00 Europe/Moscow`, `Persistent=true` при поддержке платформы; проверить `systemd-analyze calendar`. На другой инфраструктуре задать TZ явно. Не привязывать к локальному часовому поясу VPS. Catch-up при выключении допустим как восстановление пропущенного суточного цикла, а не новый плановый опрос; ручной аварийный повтор внутри того же логического запуска, не требовать от человека ежедневно. Один run lease/lock, idempotency ключ даты/источника, ограниченные ретраи с backoff внутри цикла, строгие timeouts и проверка схем. Публичные страницы не ходят к источникам. Не блокировать данные всех разделов при сбое одного.

Порядок: зафиксировать cutoff и run_id; получить изменения Zenmoney/Teamup/Telegram; staging/проверка/дедуп; транзакционно записать нормализованные факты и курсоры; рассчитать агрегаты и состояние проверенности; собрать публичный news extraction; выполнить проверки приватности/сходимости; build безопасной ревизии; атомарно опубликовать. Каждый источник отдельно last_attempt/last_success, data_as_of, coverage, ошибки, количество новых/измененных/удаленных строк. При сбое использовать последнюю успешно валидированную проекцию конкретного раздела, явно помеченную stale; не подставлять 0, не стирать данные. Если новый payload не прошёл safety-проверку, не публиковать его, оставить последнюю безопасную версию или скрыть раздел при обнаружении утечки в прежней проекции. При восстановлении продолжать с корректного курсора и сбрасывать затронутые отметки проверки. Обновлять static/CDN cache ETag с новой ревизией, не использовать stale private cache. Не инициировать повторную дорогую классификацию при каждом запросе.

Резервные копии БД, маппингов, исторических документов и состояния курсоров — раз в сутки, с проверяемым восстановлением; консистентный SQLite backup API (не копировать активный файл без WAL), шифрование и отдельное место; retention выбрать и задокументировать, не уничтожая единственную локальную копию старой истории Teamup. Секреты резервировать отдельно/зашифрованно по существующему процессу. Логи структурированные, без платежных данных, токенов, содержимого закрытых событий; healthcheck, alert при провале/потере актуальности/проблеме безопасности ответственным через выделенный согласованный канал, не публике. Hermes может мониторить, исправлять и обслуживать код; LLM не должен быть обязательным для операций, кроме новостей. Плановые расходы на API и сервер ограничивать, замерять, описать в runbook. Провести dry-run восстановления на другой чистой машине с тестовыми данными; не считать наличие backup доказательством восстановления.

## 10. Модель данных и контракты (минимум)

Реляционные таблицы/эквивалент: `source_runs`, `source_cursors`, `source_coverage`, `finance_accounts`, `finance_categories`, `finance_transactions` (private), `finance_allocations_or_classification` (только маппинг/источник, не локальная денежная поправка), `account_balance_snapshots`, `category_mapping_versions`, `calendar_occurrences` (private), `event_type_mapping`, `channel_snapshots`, `public_message_archive`, `news_items`, `news_sources`, `donor_public_aliases`, `historical_observations`, `historical_conflicts`, `checks`, `issues`, `audit_log`, `report_snapshots`, `public_releases`, `admin_members`. Foreign keys/uniqueness и миграции. Разделить исходное значение, нормализованное значение, проверенную ревизию, публичный display. Факты с ID источника и стабильным ключом. Исторический факт: metric, period_from/to, grain (`year/month/range/point`), value(nullable Decimal/int), unit, source_id, provenance (published/snapshot/derived/draft), coverage (complete/partial/unknown), confidence/status, conflict_group, notes, ingested_at. Исторический агрегат НЕ транзакция и НЕ событие. Суммирование не должно дважды добавлять период при пересечении месячных/годовых наблюдений или historical/live; при совпадающих источниках хранить оба, выбрать один по documented precedence, конфликт оставить видимым; вводить `detailed_from` отдельно для каждого источника (грань фактического полного сбора, с отметкой уже имеющихся детальных данных). Период, пересекающий границу, агрегировать только неперекрывающееся целое покрытие; если оно неполно — явно маркировать сумму как частичную. Не ретрофилл из текущих балансов.

Public DTO allowlist: `period` (запрошенный и фактически покрытый), `as_of`, `release_id`, `freshness`, `verification`, `completeness`, `source_labels`, `metrics` (nullable), `categories` (без private ids), `public_events`, `event_type_aggregates`, `channel_points`, `news_items`, `public_donor_labels` (при наличии). Не включать ни поля сырого payload, ни закрытые объекты с пустым title. Данные для календаря и totals из разных проекций, чтобы не восстановить закрытые даты. Endpoint предложения: `GET /api/public/overview?period=YYYY-MM`, `/money`, `/events`, `/community`, `/chronicle`, `/reports/...`, `/export/categories.csv`. Ограничить допустимые periods и параметры, валидировать. HTML, JSON, CSV и доступные к скачиванию отчеты проверяются одинаково. Admin endpoints отдельные с CSRF/role checks, no-store, rate limit, предотвращением IDOR. Внутренний API не доступен через CORS без авторизации. Не публиковать приватные бэкапы под webroot.

## 11. Telegram-авторизация и защита админки

Telegram OAuth/OIDC (или официально поддерживаемый Telegram Login с серверной проверкой). Проверка подписи JWKS, issuer, audience, expiry, state/nonce, PKCE, HTTPS, redirect URI allowlist; использовать стабильный Telegram user ID/sub, не username. Запрашивать только минимальный scope, без телефона, права писать пользователю не нужны. Сессия secure HttpOnly SameSite, CSRF для действий, ротация, ограниченный срок, logout/revoke. Если провайдер поменял API, использовать текущий официальный протокол по документации. Подтверждение личности не равно полномочиям: авторизация по списку действующих коммунаров (allowlist, либо достоверный список закрытой группы только если группа действительно отражает состав и проверены права); подписчик публичного канала не получает доступ. Первичный список и привязку группы получить у владельца. Изменение состава через равноправно доступный механизм с аудитом, защитой от случайного отключения всех, возможностью немедленного отзыва сессий; не создавать бессменного «суперадмина» для обычной работы. Без списка действующих участников deny by default. Удаление участника отзывает доступ с ближайшей проверки, при удалении через UI немедленно. Bootstrap админ из заранее согласованного ID, не из первого вошедшего. Все секреты хранятся только серверно.

XSS sanitization (Telegram/Teamup text untrusted), SQL parameterization, secure headers/CSP, no mixed content, ограничения размера/типа загрузок, не серверный SSRF по ссылкам из сообщений, отсутствие внутренних идентификаторов в public logs/errors, запрет robots индексации админки (дополнительно к auth, не вместо). Протестировать отсутствие закрытых данных и финансовых строк в HTML, hydration JSON, JS bundle, static export, sitemap, RSS, CSV, логи ошибок, API и резервных копиях. Реальные исходники не посылать кодовым субагентам без необходимости, не передавать IP, пароли, VPS-пути и прочую инфраструктуру в общих dev-задачах. Выделенный sandbox/staging с синтетическими тестами; production secrets выдаются только интеграционному процессу. Публикация не должна раскрывать даже имена администраторов.
## 12. Восстановление истории и приоритеты источников

См. HISTORY.md и history_evidence.json. Сначала сохранять исходные утверждения и provenance, не сводить «оригинальный отчёт», локальный экспорт и концепт-инфографику в единственную правду. При расхождении между опубликованными и пересчитанными суммами: оригинальная публикация остаётся зафиксированной, оперативная проверенная версия формируется из надёжных фактов, объяснить различие и дату исправления. Даты/годы неоднозначных текстов необходимо получить из оригинального поста или metadata; до этого хранить как observations, не публиковать с категоричным годом. Никаких «пустых» выдуманных месяцев, учётные периоды/валюта/границы пространства должны быть сопоставимы. Показывать историческое покрытие по месяцам и источникам. Не создавать события из годовой суммы, транзакции из месячной суммы или точные снимки канала из графика. Умение загрузить исторические агрегаты вручную через защищенный импорт CSV/JSON — полезно, НО не редактировать текущие финансовые факты, полученные из Zenmoney; исторический импорт относится только к отдельным прошлым периодам и источникам.
